# 一个家庭可同时持有多条连接

取代 [ADR 0002](0002-multi-agent-parallel-connections.md) 的推论「多连接 = 多 agent」：多连接也可以是同一个家庭的两条连接。当一个运行中的会话挡住新会话时，该家庭另开一条连接，新会话建在那条连接上。

## 问题

`LiveAcpClient` 一实例服务一条连接、一条活跃会话：它只有一个 `sessionId`、一个 `pendingPrompt`，外来的 `session/update` 会被外来会话过滤器丢弃（ADR 0002 的前提）。

于是这条链成立：会话 A 正在跑一个 turn → 用户点「新会话」→ `session/new` 被拒绝，因为采纳会话 B 会让 A 的更新被过滤掉，A 的回合永远不结算（bug hunt #3 的注释与测试）。

这条拒绝是必要的，但它把「新会话」整个锁死了：想同时开第二个会话，只能等 A 的回合结束。

## 决定

新会话落在家庭已有的某条连接上，当且仅当那条连接能接住它：已连接、没有进行中的 turn、没有进行中的会话切换。否则，这个家庭获得一条**额外连接**——同一个端点的第二条连接——新会话建在那里。

额外连接的 id 是 `<配置 id>#<n>`，n 从 1 起。配置 id 是 UUID，不含 `#`，所以 id 不会撞。

## 决策依据

1. **ACP 的模型是一个连接多个会话。** `session/new` 加一个会话，`session/prompt` 带 `sessionId`，`session/update` 也带 `sessionId`。`session/load` 把另一个会话载进同一条连接。Panda 的单会话客户端是简化，不是协议的要求。
2. **creche 的 ACP 门就是这么服务的。** attendance 的一条门连接承载该家庭的全部会话，每个会话一条 vmm 流、一台 VM（`attendance/src/attendance/acp_door.py`；测试 `test_two_sessions_of_one_connection_get_two_streams`）。门对同一家庭的第二条连接也没有限制：vmm 的流按会话 id 认领，不按家庭。
3. **客户端类不动。** ADR 0002 已经确认 `LiveAcpClient` 是实例级的，客户端类无需改造。第二条连接就是一个新的实例。
4. **不改变闲时的行为。** 连接不忙时，新会话仍落在原来那条连接上，和今天一样。只有被运行中的会话挡住时，行为才不同。

## Considered

- **让一条连接承载多个活跃会话**（把 `pendingPrompt`、会话 id、外来会话过滤全部按会话分桶）：更贴协议，但要把 1900 行的客户端按会话拆开，且动到每一个 agent 的行为。风险大，收益小——第二条连接就够。
- **新会话总是另开一条连接**：连接数随会话数增长，每条连接一个套接字；而且对只吃一条连接的 agent 是行为变更。否决。
- **等运行中的回合结束再允许新会话**：保持现状，用户仍然拿不到并行的第二个会话。否决。

## Consequences

- 一个家庭同时可以有几条连接：用户点几次「新会话」就有几条。一个运行中的 turn 挡住一条连接，另一条连接照样接新会话。
- 侧栏的合并列表按「端点 + 会话 id」去重。两个连接共享端点，也就共享会话列表，同一个会话会到达两次。持有该会话的连接优先——点击要前台化的正是那条持有它的连接。
- 家庭的状态点聚合该家庭的全部连接：任一条连接在跑 turn，状态点就显示运行中。
- 家庭被删除时，它的额外连接一起删除。
- 额外连接不是配置：它不保存，不随浏览器保留。刷新页面后只剩该家庭的主连接，它从 `session/list` 里认回那些会话。
